上一章[同步与通信](../4_ipc/同步与通信.md)补上了线程间的同步与通信，内核的功能已经基本完整了。这一章我们来进行性能测试，看看 mimiOS 的性能如何。

# 测试环境

项目三套内核跑在完全相同的硬件和编译环境上：

- 测试平台：STM32L452RE，Cortex-M4，主频 80 MHz。
- 编译选项：关闭 FPU，-O2，无 LTO，禁用断言。
- OS 选项：32 个优先级，关闭 trace / stats / 栈溢出检查 / 各类 hook，开启函数内联宏。

# Thread-Metric-Benchmark

Thread-metric 的测试内容：让 RTOS 在固定时间间隔内反复执行同一类操作，统计完成次数，数据能够表示内核处理能力的带宽以及稳定性。测试套件的地址是 [thread-metric-benchmark](https://github.com/sysprog21/thread-metric-benchmark)，源自微软 ThreadX 仓库。网上有基于这个套件的两份测试报告 [2024 年](https://www.esbf.org/wp-content/uploads/2024/10/Beningo_RtosPerformance_20241021.pdf) 和 [2026 年](https://us.list-manage.com/yrMv9GX_vtv?e=3cc255de94&c2id=3cf27be992ffd01adbd85a7d1de657c9&i=080a64b390)

## 测试内容

Thread-metric 每次报告会打印 Time Period Total，也就是周期的操作计数。多个周期连续报告，取稳定值。同时测试带有稳定性检查，比如协作调度的 5 个线程计数必须接近，否则报错，用来抓调度不公平的问题。

Thread-metric 一共有 8 项测试内容，我们选取 mimiOS 已经实现的内容进行测试。项目仓适配了 FreeRTOS 和 ThreadX，我们就用这两个 RTOS 作为对比。

| 测试项目                       | 内容                                 |
| -------------------------- | ---------------------------------- |
| Basic Processing           | 单线程纯计算，作为 CPU 能力基线                 |
| Cooperative Scheduling     | 协作式调度测试，同优先级 5 个线程轮转，线程计数+1，然后让出 CPU |
| Preemptive Scheduling      | 优先级抢占测试，线程释放高一级优先级线程，计数+1，然后让出 CPU |
| Message Processing         | 消息队列测试，单线程 16 字节消息收发，完成一轮计数+1        |
| Synchronization Processing | 同步原语测试，单线程信号量获取和释放，完成一轮计数+1        |

# RTOSBench

RTOSBench 关注 RTOS 内核服务的性能，统计测试项目的运行周期。测试套件的地址是 **[RTOSBench](https://github.com/gchamp20/RTOSBench)**，网上也能找到基于该套件的测试报告 [Measuring RTOS Performance](https://www.ul.com/sis/blog/measuring-real-time-operating-system-performance-part-ii-comparing-freertos-vs-zephyr#1)

测试使用的计时源是 Cortex-M 的 DWT（ARM CoreSight 调试架构中的一个硬件单元，主要用于**数据观察点、性能计数和跟踪触发**），单位为 cycles（80 MHz，1 cycle = 12.5 ns）。

我们选用上述测试报告使用的 FreeRTOS 和 Zyphyr 作为对比。测试结果每项包含 avg/max 两个数据，代表通用耗时和最坏耗时，体现 RTOS 的实时性。

## 信号量

测试内容包含四个测试文件，每个文件侧重不同

### sem_processing.c

单线程工作，分别测量「释放」和「获取」信号量的时长，不涉及上下文切换。

### sem_prio.c

三个优先级线程：TA 高、TB 中、TC 低。测试逻辑为：TB 阻塞等待信号量，TA 释放信号量，TB 被移到就绪队列，测量窗口是「释放信号量 + 把等待任务移入就绪队列」，没有上下文切换。
### sem.c

sender 低优先级，receiver 高优先级，分为两个测试窗口：

- 「获取阻塞 + 切出」，测量 receiver 阻塞等待信号量，然后切换到其他线程的时长。
- 「释放 + 唤醒切换」，测量 sender 释放信号量，然后切换到 receiver 的时长。
### sem_workload.c

核心测试指标也是「释放 + 唤醒切换」，区别在于每轮之间隔了 10 ms，刷新了 cache 和流水线，更接近真实应用场景。
