# 线程同步

线程同步主要处理下面两种情况：

1. 线程需要等待资源就绪，才能进行后续任务，例如线程获取 socket 资源，可以使用信号量表示可用数量；
2. 避免多个线程同时使用共享资源，例如两个线程共用同一条 I2C 总线，需要防止被抢占导致时序混乱，即使是更高优先级线程也不可以抢占。需要互斥锁来保护共享资源。

## 信号量

信号量是一个带上限的计数器，用来表示某个资源可用数量，或者当成二元信号量，表示某个事件是否发生。最大的作用可以阻塞和唤醒，构成准确的异步链条：

- take（P 操作）：计数减一，减到 0 之后，线程阻塞等待。
- release（V 操作）：计数加一，如果等待队列非空，唤醒队首的线程。

### 获取信号量

获取信号量的行为分为两种情况：
1. 信号量大于一，成功获取；
2. 信号量等于零，根据同步语义，我们可以设定一个超时时间，让线程进入阻塞等待；

我们得到了信号量的结构体定义：
```c
typedef struct {
    uint32_t      max_cnt;       // 计数上限
    uint32_t      cnt;           // 当前计数
    mimi_list suspend_list;
} mimi_sem;
```

重点在超时等待和阻塞恢复。超时等待通过系统软件定时器完成，超时则唤醒线程，返回失败。阻塞等待然后成功获取信号量的路径，通过释放信号量的函数完成。mimiOS 信号量阻塞队列设计为按照优先级排列，也是抢占调度的一种体现。

### 释放信号量

`release` 函数首先判断等待队列是否为空，非空则弹出队首的线程并唤醒它。如果没有阻塞的线程，再增加计数器，这样能够减少计数修改，防止bug；

### 中断通知线程

信号量最常见的用法，是中断通知线程。中断里避免做耗时操作，把中断的下半部分交给线程处理。中断里调用 `release` 是安全的，它不阻塞，只计数和唤醒。线程里调用 `take` 才可能阻塞，这正合适：等待发生在线程里，中断保持简短。

```c
mimi_sem rx_sem;

// 串口接收中断
void UART_Rx_ISR(void)
{
    mimi_sem_release(&rx_sem);    // 通知有数据了
}

// 处理线程
void uart_proc_entry(void *param)
{
    while (1) {
        mimi_sem_take(&rx_sem, MIMI_TIMEOUT_FOREVER);   // 等数据
        // 处理收到的数据
    }
}
```

## 互斥锁

信号量用来同步等待资源，互斥锁用来保护共享资源，进行独占访问。

### 保护共享数据

举个例子。`shared_cnt++` 这行代码，编译后是读变量、加一、写回三条指令。程序运行时线程可能在任意位置切换，在读变量后被切走，切回来已经是一个旧的变量了，两个线程各加 10000 次，结果可能不是 20000。互斥锁把 `shared_cnt++` 变成原子操作，同一时刻只有一个线程能进入临界区。
```c
void worker_entry(void *param)
{
    for (int i = 0; i < 10000; i++) {
        mimi_mutex_lock(&mtx, MIMI_TIMEOUT_FOREVER);
        shared_cnt++;
        mimi_mutex_unlock(&mtx);
    }
}
```
一般情况下，互斥锁的获取释放逻辑跟二值信号量一致。为了防止一个线程多次获取同一把锁导致死锁，我们增加一个嵌套支持，这样我们得到了互斥锁的结构体定义：
```c
typedef struct {
    uint8_t       lock_nest;
    mimi_tcb      *owner;
    mimi_list     suspend_list;
} mimi_mutex;
```
1. `owner` 记录持有者，进行嵌套锁，同时校验解锁时是否同一线程的动作；
2. `lock_nest` 嵌套计数，mimiOS 的互斥锁支持同一线程嵌套上锁，最后一次解锁才是真正对外解锁。

### 优先级翻转

先来看一个举个例子：有三个线程，优先级从高到低是 A、B、C。

1. C 先获取锁，进入临界区。
2. A 也请求这把锁，因为锁被占用，只能阻塞等 C 释放。
3. 这时 B 就绪。B 优先级高于 C，抢占 C 的 CPU。
4. C 拿不到 CPU，无法释放锁，A 只能继续等。

结果是最高的 A 等最低的 C，中间又被 B 卡住。A 的有效优先级被拉低到 C 的水平，这就是优先级翻转问题。

![[优先级翻转.svg|85%]]


有个著名的例子：1997年，搭载着 VxWorks 的火星探路者着陆后反复重启，查了很久才发现，一个低优先级的气象任务持有了高优先级任务需要的锁，被中优先级的通信任务持续抢占，导致高优先级任务超时，触发看门狗重启。

我们可以通过**优先级继承**机制规避这个问题，A 请求锁的时候，将 C 的优先级提升到 A 的级别，当会人上人，防止被 B 抢占，C 释放锁的时候再恢复其原有的优先级。有一个需要注意的地方，一个线程可能会持有多个锁，真正恢复优先级需要等到所有锁都释放，防止直接恢复到低优先级又导致优先级翻转。所以在 mimi_tcb 中 增加了变量 mtx_hold ，用于记录线程持有锁的数量。

# 线程通信

mimiOS 将实现两种通信机制：消息队列传输固定长度的消息，无锁 RingBuffer 传输不定长的字节流。

## 消息队列

通过消息队列，我们可以将数据采集和处理分为两个线程，分别赋予不同优先级，两个线程能够解耦开来，独立实现。

首先来定义消息队列的数据结构，mimiOS 的消息队列设计为每条消息长度固定，数据缓冲区被划分成 `capacity` 个槽，每个槽放一条消息，本质上是一个数组结构的环形缓冲区。

我们还需要指向数据读写位置的索引，`prod` 指向下一个空槽，新消息从这里入队；`cons` 指向下一个待读槽，消息从这里出队。两个指针只在 `buffer` 和 `end` 划定的范围内移动，走到 `end` 就回到 `buffer`，构成一个环形。

类似线程同步，最后加上接收等待队列，我们得到了消息队列的结构体定义：
```c
typedef struct {
    uint32_t msg_size;             // 每条消息长度（字）
    uint32_t capacity;             // 槽位数量
    uint32_t cnt;                  // 当前消息数

    unsigned long *prod;           // 写指针，指向下一个空槽
    unsigned long *cons;           // 读指针，指向下一个待读槽
    unsigned long *buffer;         // 缓冲区起点
    unsigned long *end;            // 缓冲区终点

    mimi_list recv_suspend_list;   // 等待消息的线程队列
} mimi_mqueue;
```

### 发送消息

我们根据缓冲区和接收队列的情况分类讨论：

1. 先看接收等待队列，如果非空，我们可以直接将消息拷贝到等待线程的 buffer，不经过队列，减少一次中转损耗。mimiOS 将等待线程的 buffer 记录到到 `TCB->mq_buffer`，阻塞等待前赋值到该变量上。
2. 等待队列是空的，缓冲区未满，将数据拷贝到缓冲区，然后推进 prod 指针

如果缓冲区已满，不得不丢掉一些数据，该丢掉那一份呢，我们可以通过 flag 控制

- `MIMI_MQ_FULL_DROP` 丢弃本次数据，返回发送失败；
- `MIMI_MQ_FULL_OVERWRITE` 覆盖最旧的一条消息；
- `MIMI_MQ_URGENT` 紧急消息插队，接收者会先取到它。队列没有满时，数据写到队头的前一格，读指针后退一格；队列已满时，则覆盖最旧的一条消息。

### 消息拷贝

对消息队列性能影响最大的是数据拷贝。每收发一条消息，内核就要复制一次 `msg_size` 的数据，收发循环里大部分时间都花在拷贝上，加锁、推进指针相比之下都是小头，拷贝方式直接决定队列的吞吐。

最直接的思路是按字拷贝。Cortex-M 是 32 位机，寄存器一次能搬 4 个字节，逐字节拷贝同样的数据要多跑四倍的循环，按字拷贝把循环次数压到四分之一。

gcc 提供了内建的 `__builtin_memcpy`，编译器认识这个函数，能根据情况优化：长度是编译期常量且不大时，它直接把拷贝展开成几条 ldr 和 str；长度是运行期变量时，它回落到库函数，库里要先检查两端地址的对齐情况，按字对齐后逐字搬运，尾部不足一个字的部分再逐字节补齐。这些检查对任意长度、任意对齐的输入都有必要，但消息队列用不上。

mimiOS 的消息队列在初始化时就已经锁死了这些条件：`msg_size` 是 4 的倍数，断言保证；缓冲区地址按字对齐。长度和地址都对齐了，通用 memcpy 里的对齐检查、尾部处理全是白做的，于是最终选择手写一个逐字拷贝：

```c
mimi_inline void mq_copy_words(void *dst, const void *src, uint32_t words)
{
    uint32_t *d = (uint32_t *)dst;
    const uint32_t *s = (const uint32_t *)src;

    while (words--) {
        *d++ = *s++;
    }
}
```

函数按 `uint32_t` 逐字搬运，编译器把它优化成 ldr 和 str 的循环，每轮搬 4 个字节，没有任何分支。发送和接收的所有复制路径都走这个函数。

### 接收消息

接收消息的行为分两种情况：

1. 队列里有消息，接收函数从 `cons` 槽复制出数据，`cons` 前移，`cnt` 减一，立即返回；
2. 队列为空，接收函数按超时参数处理：参数指定不等待，就返回错误；否则线程阻塞进入等待队列。

线程阻塞之前要做两件准备工作。接收函数先把接收缓冲挂到 `mq_buffer` 字段，这是留给发送方直达复制的位置；再把线程挂到 `recv_suspend_list`，同时装上超时定时器，最后让出 CPU。阻塞和唤醒的机制跟信号量的一样。

## 无锁队列

### 不定长的字节流

消息队列按条处理，长度固定，一进一出都是完整的一条。无锁队列是字节流，长度随意，写多少读多少，不关心消息边界。

日志是最典型的场景。日志长度不定，一条可能几个字，一条可能几百字，还可能同时来自好几个线程甚至中断。用固定长度消息队列存日志，要么浪费，要么放不下。字节流没有这个问题，写入的是连续字节，读出后再按行切分。

### 无锁原理

mimiOS 的 `ringbuffer.c` 是一个多生产者单消费者（MPSC）的无锁环形缓冲，思路参考 DPDK 的 ring buffer。整套设计只依赖一个原语，CAS。

CAS（compare-and-swap）把比较和交换封装成一次原子操作，用法是 `CAS(ptr, old, new)`。`ptr` 是目标地址，`old` 是这个地址不久前的值，`new` 是准备写入的新值。处理器执行 CAS 时，先比较 `ptr` 当前的值是否还等于 `old`，相等就把 `new` 写进去，比较和写入一次完成，中间不会插入其他执行流；不相等就写入失败，调用方取回 `ptr` 的新值，再重试一次。mimiOS 用 gcc 的内建函数实现它：

```c
#define CAS(P, O, V)  __sync_bool_compare_and_swap((size_t *)(P), (O), (V))
```

在 Cortex-M 上，这个内建函数展开为 ldrex 和 strex 指令对。ldrex 标记一段独占访问，strex 只有在这段独占没有被破坏时才会成功，两个指令之间来了别的写操作，strex 就失败重来。宏观上没有锁，微观上是 CPU 的一条极小的硬件保证，无锁这个名字就是这么来的。

CAS 有一个著名的缺陷，ABA 问题。CAS 只判断值等不等于旧值，它区分不了值一直没变，和值变过又改回来这两种情况。经典的出错场景在链表上：线程 A 读到头节点 x，准备做 CAS；线程 B 把 x 从链表摘下来释放，又把新分配的节点放回链表头，新节点恰好复用了 x 的地址；线程 A 的 CAS 比较 x 相等，操作成功，但链表的实际结构已经变了，A 的后续操作就在错误的结构上进行。

ringbuffer 不需要担心 ABA，因为这里的三个指针都是单调递增的位置，不是循环使用的地址。`prod_head` 只会前进，一个生产者以 `old_head` 作为旧值做 CAS，只要期间有其他生产者成功推进过，`prod_head` 就再也不可能等于 `old_head`，CAS 必然失败重试。要让 `prod_head` 回到旧值，需要整整回绕 2 的 32 次方字节，在这个缓冲区上不可能发生。ABA 真正危险的地方是内存被释放又复用的场景，而 ringbuffer 的缓冲区在初始化之后固定不变，没有复用问题。

### 入队

mimiOS 把写入拆成两步：先申请位置，再提交。我们得到了 ringbuffer 的结构体定义：

```c
typedef struct {
    volatile uint32_t prod_head;   // 生产者抢占的写位置
    volatile uint32_t prod_tail;   // 生产者提交的写位置
    volatile uint32_t cons;        // 读位置，只有消费者写
    uint32_t          capacity;    // 容量，必须是 2 的幂
    uint8_t           buffer[];    // 柔性数组，调用方分配
} mimi_ringbuffer;
```

三个指针各管一段边界，都是单调递增的位置，通过位与映射到物理地址：

- `prod_head` 是生产者抢到的最远写位置，多个生产者用 CAS 竞争推进它；
- `prod_tail` 是已经写完、可以读的位置，消费者只读到 `prod_tail` 为止；
- `cons` 是消费者读到的位置，只有消费者修改它，不需要原子操作。

![[无锁队列.svg|85%]]

写入分三步。第一步申请位置，生产者用 CAS 自旋推进 `prod_head`：

```c
static mimi_err update_prod_head(mimi_ringbuffer *ring, uint32_t len,
                                 uint32_t *old_head, uint32_t *new_head)
{
    do {
        *old_head = ring->prod_head;             // 读当前写位置
        if (get_space(ring) < len) {
            return MIMI_ERROR;                   // 空间不够
        }
        *new_head = *old_head + len;
    } while (!CAS(&ring->prod_head, *old_head, *new_head));   // 抢占失败就重试
    return MIMI_EOK;
}
```

CAS 成功的生产者拿到 `[old_head, new_head)` 这一段的独占写权，其他生产者 CAS 失败，重新读取 `prod_head` 再试。空间检查以 `prod_head` 为准，已申请未提交的位置也算作已用，这个估计偏保守，但保证两个生产者不会申请到重叠的区域。

第二步往自己那一段写数据。数据写到缓冲区尾部就绕回头部，分两段复制完成。

第三步提交，推进 `prod_tail`：

```c
static void update_prod_tail(mimi_ringbuffer *ring, uint32_t old_head,
                             uint32_t new_head)
{
    while (!CAS(&ring->prod_tail, old_head, new_head)) {
        mimi_nop();                              // 前面的段还没提交，等它
    }
}
```

提交可能乱序。两个生产者先后申请位置，先申请的可能后写完，如果各自直接推进 `prod_tail`，提交边界就会跳过未写完的数据。CAS 的比较条件保证了顺序，`prod_tail` 只有等于自己的 `old_head` 时才能推进到 `new_head`，否则自旋等待，等前面的段先提交。消费者只看 `prod_tail`，它之前的数据一定完整。

提交还藏着一个内存屏障问题。生产者先写数据，再提交 `prod_tail`，如果另一个核心先看到 `prod_tail` 更新、后看到数据，就会读到垃圾。gcc 的 CAS 自带完整的内存屏障，提交那一次 CAS 保证了数据写入先于指针推进对其他核心可见，这个问题不需要额外处理。

### 出队

读取比写入简单，因为消费者只有一个。读函数先用 `prod_tail - cons` 算出可读的数据量，这是已提交的数据边界；再显式执行一次内存屏障，保证先看到 `prod_tail` 的更新、后读取数据；然后从 `cons` 开始拷贝，数据跨过缓冲区尾部就分两段拷贝；最后把 `cons` 前移。`cons` 只有消费者一个写入者，前移是普通赋值，不需要原子操作。

### 无锁的意义

无锁队列最大的价值，是中断里也能安全地写。

线程写入队列上锁期间，中断内部再获取锁就会失败，由于中断不能阻塞，数据相当于丢掉了。使用无锁队列，中断的数据正常写入，线程一侧的 CAS 失败，重新申请写入位置，两边的数据都正常入队。

同样的竞争在多核场景更常见，两个核心上的线程会同时写同一个 ringbuffer。加锁的方案要面对三个问题：自旋锁把所有访问串行化，等待者空转烧 CPU；锁的持有者可能跑在另一个核上，优先级继承这类单核手段失效；锁本身也要靠原子操作实现，临界区越长风险越大。无锁队列把同步缩小到一次 CAS：两个核心的生产者同时申请位置，谁 CAS 成功谁先写，失败者重新读取位置再试；数据可见性由 CAS 自带的内存屏障保证，先看到 `prod_tail` 更新的核心一定能看到完整数据。mimiOS 跑在单核 M4 上，这套设计参考自 DPDK，本身是为多核网络处理器准备的，将来移植多核不需要推翻重来。

# 例子

现在我们有了多种 IPC 模块，可以搞点实际的东西

## 异步 log 模块

第三章的日志是同步的，`printf` 直接输出到串口。串口发送是慢操作，一个线程打印一行，整个线程就阻塞在串口发送上，等发送完成才能继续。

这一章把日志改成异步的：写日志只往无锁队列里写字节，写完就返回；一个专门的日志线程负责把队列里的字节输出到串口。

```c
struct {
    mimi_ringbuffer ring;
    uint8_t buffer[MIMI_LOG_BUFFER_SIZE];
} log_ringbuffer;

mimi_sem log_sem;
```

写日志先格式化到临时缓冲，再写进 ringbuffer，最后 release 信号量：

```c
void mimi_log_printf(char level, const char *fmt, ...)
{
    char print_buffer[LOG_TEMP_BUFFER_SIZE];
    // 拼上时间戳、级别、线程名
    ...
    if (mimi_ringbuffer_write(&log_ringbuffer.ring, print_buffer, len) == MIMI_EOK) {
        mimi_sem_release(&log_sem);   // 通知日志线程有活了
    }
}
```

日志线程阻塞在信号量上，被唤醒就把队列读空，交给输出函数：

```c
void mimi_log_thread_entry(void *param)
{
    while (1) {
        mimi_sem_take(&log_sem, MIMI_TIMEOUT_FOREVER);
        while ((len = mimi_ringbuffer_read(&log_ringbuffer.ring,
                read_buffer, LOG_TEMP_BUFFER_SIZE)) > 0) {
            mimi_log_output_func(read_buffer, len);
        }
    }
}
```

这里信号量和无锁队列各司其职：信号量表示有日志到达，唤醒日志线程；无锁队列保存日志字节。写日志的调用方可能是任何线程甚至中断，只做两件事：写 ringbuffer、release。真正访问串口的只有日志线程，串口的慢被隔离在这个线程里，不影响其他线程。

中断里也能输出日志了。日志线程被唤醒前，中断写入队列的字节已经完整，等日志线程醒来统一输出，这正是第三章说的把工作交给线程处理。

## 简易控制台

有了异步日志，再加一个命令解析线程，就是个简易控制台。串口收到一行命令，交给控制台线程，匹配注册的命令，执行对应函数。

命令注册沿用了自动初始化的思路，把命令函数地址放到 `.mimi_cmd_fn` 段：

```c
#define MIMI_CMD_EXPORT(cmd, fn)                                \
    const char __mimi_cmd_##cmd[] = #cmd;                       \
    mimi_used const struct mimi_cmd_desc __mimi_cmd_desc_##fn   \
        mimi_section(".mimi_cmd_fn") = { __mimi_cmd_##cmd, fn };
```

业务代码里加一条命令：

```c
int sem_test(void) { ... }
MIMI_CMD_EXPORT(semtest, sem_test);
```

控制台线程轮询输入，收到一行就去命令段里查名字，匹配就执行：

```c
void mimi_console_thread_entry(void *param)
{
    while (1) {
        uint16_t len = mimi_console_input_func(console_buffer, CONSOLE_TEMP_BUFFER_SIZE);
        mimi_console_input((const char *)console_buffer, len);
    }
}
```

串口敲一个 `semtest`，信号量的例子就跑起来了。

## 基础用例演示

这一章用单元测试验证信号量、互斥锁、消息队列的状态转换，用真实线程验证无锁队列的并发写。

| 模块 | 验证内容 | 验证方式 |
| ---- | -------- | -------- |
| 信号量 | 计数增减、减到 0 阻塞、超时返回、唤醒队首 | 单元测试 |
| 互斥锁 | 加解锁、递归、非持有者解锁被拒绝、优先级继承接口 | 单元测试 |
| 消息队列 | 收发、环形回绕、空阻塞、满拒绝 | 单元测试 |
| 无锁队列 | 2 的幂容量、环绕、多生产者数据完整性 | 单元测试 + 多线程 |

单元测试用 Unity 框架，跑在 native 环境，不依赖硬件，执行 `pio test -e unit`。

无锁队列的并发写比较特殊：要真正确认多生产者同时写不丢数据，得用多个真实线程并发写。测试里用 Win32 的 `CreateThread`（Linux 上是 pthread）创建 4 个生产者，每个往同一个 ringbuffer 写带线程编号的字节，消费者读出后按编号分类核对，确认每个生产者写入的字节一个没丢、顺序也没乱。

三个例子 `semaphore.c`、`mutex.c`、`msgqueue.c` 则跑在板子上，通过控制台命令触发。互斥锁的例子最直观：两个线程各加 50 次 `shared_cnt`，串口打印的计数应该严格递增到 100，中间不会重复、不会跳变。不加锁的话，很快就能看到计数错乱。
