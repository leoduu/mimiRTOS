# 线程间同步

同步处理两类情况：线程需要等待某个条件，以及共享数据只能被一个线程访问。前者用信号量，后者用互斥锁。

## 信号量

信号量是一个带上限的计数器，用来表示某个资源还剩多少份，或者某个事件是否已经发生。

- take（P 操作）：计数减一，如果减到 0 之后还想减，就阻塞等待。
- release（V 操作）：计数加一，如果等待队列非空，就唤醒队首的线程。

```c
typedef struct {
    mimi_node     node;
    mimi_spinlock lock;
    uint32_t      max_cnt;       // 计数上限
    uint32_t      cnt;           // 当前计数
    mimi_list     suspend_list;  // 等待队列
} mimi_sem;
```

上限 `max_cnt` 代表可用资源，例如 socket 可用数量。`max_cnt = 1` 是二元信号量，常用来当事件标志；

### 阻塞与唤醒

`take` 先获取锁，再检查计数。如果计数不为零，就把计数减一并返回；如果计数为零，就把当前线程挂到等待队列上，然后让出 CPU。

```c
mimi_err mimi_sem_take(mimi_sem *sem, uint32_t timeout)
{
    mimi_tcb *curr = mimi_thread_current();
    uint32_t level = mimi_spin_lock(&sem->lock);

    if (sem->cnt == 0) {
        if (timeout == MIMI_TIMEOUT_NOWAIT) {
            mimi_spin_unlock(&sem->lock, level);
            return MIMI_ERESOURCE;
        }
        mimi_thread_suspend_to_list(curr, timeout, &sem->suspend_list);
        mimi_spin_unlock(&sem->lock, level);
        mimi_schedule();                  // 让出 CPU

        // 被唤醒后从这里继续，检查唤醒原因
        level = mimi_spin_lock(&sem->lock);
        if (curr->timer.status == MIMI_TIMER_TIMEROUT) {
            mimi_list_remove(&sem->suspend_list, &curr->node);
            mimi_spin_unlock(&sem->lock, level);
            return MIMI_ETIMEOUT;         // 超时了，不是有信号
        }
    }

    sem->cnt--;
    mimi_spin_unlock(&sem->lock, level);
    return MIMI_EOK;
}
```

几个要点：

1. `mimi_spin_lock` 关中断拿锁。临界区很短，只保护计数器和链表，阻塞不发生在锁里。
2. `mimi_thread_suspend_to_list` 把线程从就绪队列摘下来，挂到信号量的等待队列，同时给线程装一个超时定时器。
3. `mimi_schedule()` 主动让出 CPU，切到别的线程。
4. 被唤醒后要判断原因：是其他线程调用了 release，还是超时。如果超时，就把自己从等待队列摘掉，返回 `MIMI_ETIMEOUT`。

`release` 更简单：计数加一，如果等待队列非空，就弹出队首的线程并唤醒它。

```c
mimi_err mimi_sem_release(mimi_sem *sem)
{
    uint32_t level = mimi_spin_lock(&sem->lock);
    sem->cnt++;
    if (sem->cnt > sem->max_cnt) {
        sem->cnt = sem->max_cnt;
    }
    if (!mimi_list_empty(&sem->suspend_list)) {
        mimi_tcb *thread = container_of_tcb(sem->suspend_list.head);
        mimi_list_pop_front(&sem->suspend_list);
        mimi_spin_unlock(&sem->lock, level);
        mimi_thread_wakeup_from_ipc(thread);
        return MIMI_EOK;
    }
    mimi_spin_unlock(&sem->lock, level);
    return MIMI_EOK;
}
```

释放时先弹出队首，再唤醒。被唤醒的线程如果优先级更高，`mimi_thread_wakeup_from_ipc` 内部会触发调度，立刻切换过去。

### 中断通知线程

信号量最常见的用法，是中断通知线程。第三章说过，中断里不能做耗时操作，应该把工作交给线程处理。具体做法是：中断里调用 `release`，线程里调用 `take`。

```c
mimi_sem rx_sem;

// 串口接收中断
void UART_Rx_ISR(void)
{
    mimi_sem_release(&rx_sem);    // 通知有数据了
}

// 处理线程
void uart_proc_entry(void *param)
{
    while (1) {
        mimi_sem_take(&rx_sem, MIMI_TIMEOUT_FOREVER);   // 等数据
        // 处理收到的数据
    }
}
```

中断里调用 `release` 是安全的，它不阻塞，只计数和唤醒。线程里调用 `take` 才可能阻塞，这正合适：等待发生在线程里，中断保持简短。

## 互斥锁

信号量用来等待，互斥锁用来独占访问。

互斥锁和二元信号量最本质的区别在于所有权。谁 lock 的，只能谁 unlock，别人 unlock 会报错。二元信号量没有所有权，谁都能 release。所以互斥锁适合保护临界区，信号量适合做事件通知。

### 保护共享数据

一个具体例子。`shared_cnt++` 这行 C 代码，编译后是读、加一、写回三条指令。两个线程交错执行，就会丢计数：两个线程各加 1000 次，结果可能不是 2000。

```c
mimi_mutex mtx;
int shared_cnt = 0;

void worker_entry(void *param)
{
    for (int i = 0; i < 1000; i++) {
        mimi_mutex_lock(&mtx, MIMI_TIMEOUT_FOREVER);
        shared_cnt++;
        mimi_mutex_unlock(&mtx);
    }
}
```

锁把 `shared_cnt++` 变成原子操作，同一时刻只有一个线程能进入临界区。

### 结构与实现

```c
typedef struct {
    mimi_node     node;
    mimi_spinlock lock;
    uint8_t       lock_cnt;       // 嵌套计数
    uint8_t       highest_prio;   // 等待者里的最高优先级
    mimi_tcb     *thread;         // 当前持有者
    mimi_list     suspend_list;   // 等待队列
} mimi_mutex;
```

比信号量多了两个字段。`thread` 记录持有者，unlock 时校验是不是自己 lock 的。`lock_cnt` 支持嵌套，同一个线程可以 lock 多次，unlock 同样多次才真正释放。

```c
mimi_err mimi_mutex_lock(mimi_mutex *mtx, uint32_t timeout)
{
    uint32_t level = mimi_spin_lock(&mtx->lock);
    mimi_tcb *curr = mimi_thread_current();

    if (curr == mtx->thread) {          // 递归锁，计数加一
        mtx->lock_cnt++;
    } else {
        if (mtx->lock_cnt > 0) {        // 被别人持有
            if (timeout == MIMI_TIMEOUT_NOWAIT) {
                mimi_spin_unlock(&mtx->lock, level);
                return MIMI_ERESOURCE;
            }
            // 记录等待者优先级，挂起等待
            mimi_thread_suspend_to_list(curr, timeout, &mtx->suspend_list);
            ...
        }
        mtx->lock_cnt = 1;
        mtx->thread = curr;             // 拿到锁，成为持有者
    }
    mimi_spin_unlock(&mtx->lock, level);
    return MIMI_EOK;
}
```

unlock 时先校验持有者，如果调用者不是持有者就直接拒绝；计数减到 0 才真正释放，如果有等待者就唤醒一个，没有就把锁置空。

### 优先级翻转

互斥锁有个经典问题：优先级翻转。

三个线程，优先级从高到低是 A、B、C。

1. C 先获取锁，进入临界区。
2. A 也请求这把锁，因为锁被占用，只能阻塞等 C 释放。
3. 这时 B 就绪。B 优先级高于 C，抢占 C 的 CPU。
4. C 拿不到 CPU，无法释放锁，A 只能继续等。

结果是最高的 A 等最低的 C，中间又被 B 卡住。A 的有效优先级被拉低到 C 的水平，这就是优先级翻转。

![[优先级翻转.svg|85%]]

最著名的例子是火星探路者。1997 年它着陆后反复重启，查了很久才发现就是优先级翻转：一个低优先级的气象任务持有了高优先级任务需要的锁，被中优先级的通信任务持续抢占，导致高优先级任务超时，触发看门狗重启。

解法是优先级继承：A 等 C 的锁时，把 C 的优先级临时提到 A 的高度，让 C 尽快执行完临界区并释放锁，再恢复 C 的优先级。这样 B 无法抢占 C，A 的等待时间被压到最短。

mimiOS 的互斥锁提供了这套接口：`highest_prio` 记录等待者中的最高优先级，`mimi_thread_prio_raise` 临时提升优先级，`mimi_thread_prio_recover` 恢复原优先级。优先级继承由这组接口实现。

# 线程间通信

同步处理等待和独占，通信处理数据传递。线程之间传数据有两条路：消息队列传一条条固定长度的消息，无锁队列传一段段不定长的字节。

## 消息队列

### 使用场景

一个线程采集数据，一个线程处理数据。采集线程每采一帧，就把数据写入队列；处理线程从队列读取，取到就处理，取不到就阻塞等。两个线程就此解耦：采集线程不关心谁在消费，处理线程不关心数据从哪来。

```c
// 采集线程
mimi_mqueue_send(&mq, &frame);

// 处理线程
mimi_mqueue_recv(&mq, &frame, MIMI_TIMEOUT_FOREVER);
```

### 固定长度消息

mimiOS 的消息队列，每条消息长度固定。初始化时确定 `msg_size`，缓冲区被划分成 `capacity = buffer_size / msg_size` 个槽，每个槽放一条消息。

```c
typedef struct {
    mimi_node     node;
    mimi_spinlock lock;
    uint16_t      msg_size;            // 每条消息长度
    uint16_t      capacity;            // 槽位数量
    uint16_t      cnt;                 // 当前消息数
    uint16_t      prod;                // 写指针
    uint16_t      cons;                // 读指针
    void         *buffer;              // 消息缓冲区
    mimi_list     recv_suspend_list;   // 等消息的线程
} mimi_mqueue;
```

`prod` 和 `cons` 是一对读写指针，配合 `capacity` 取模，构成一个环形。写入时，先把数据 `memcpy` 到 `prod` 指向的槽，再把 `prod` 前移；读取时，先从 `cons` 指向的槽 `memcpy` 出来，再把 `cons` 前移。消息是整体复制的，进入队列后就和发送方的缓冲区没有关联了。

固定长度有好处：内存布局规整，槽位地址可以直接算，`prod` 到 `cons` 之间就是待消费的消息，不会出现半条。代价是每条消息都按最长的算，短的也占满一个槽。消息长度差异大的场景，更适合用字节流。

### 实现

`send` 在队列已满时直接返回 `MIMI_ERESOURCE`，不阻塞：

```c
mimi_err mimi_mqueue_send(mimi_mqueue *mq, const void *buffer)
{
    uint32_t level = mimi_spin_lock(&mq->lock);
    if (mq->cnt == mq->capacity) {
        mimi_spin_unlock(&mq->lock, level);
        return MIMI_ERESOURCE;        // 满了，不阻塞
    }
    void *prod_ptr = (uint8_t *)mq->buffer + mq->msg_size * mq->prod;
    memcpy(prod_ptr, buffer, mq->msg_size);
    mq->prod = (mq->prod + 1) % mq->capacity;
    mq->cnt++;
    // 有线程在等消息，唤醒一个
    ...
}
```

`recv` 在队列为空时阻塞等待，直到有消息或超时，过程和信号量的 `take` 一样：挂到等待队列，让出 CPU，醒来后检查唤醒原因。

消息队列和信号量常搭配出现。典型的中断收数据流程：中断里调用 `send` 往队列写数据，线程里调用 `recv` 阻塞等。信号量表示有数据到达，消息队列传递数据本身。

## 无锁队列

### 不定长的字节流

消息队列按条处理，长度固定，一进一出都是完整的一条。无锁队列是字节流，长度随意，写多少读多少，不关心消息边界。

日志是最典型的场景。日志长度不定，一条可能几个字，一条可能几百字，还可能同时来自好几个线程甚至中断。用固定长度消息队列存日志，要么浪费，要么放不下。字节流没有这个问题，写入的是连续字节，读出后再按行切分。

### 无锁原理

mimiOS 的 `ringbuffer.c` 是一个多生产者单消费者（MPSC）的无锁环形缓冲，思路参考 DPDK 的 ring buffer。

关键是把写入拆成两步：先申请位置，再提交。所有生产者用 CAS（compare-and-swap）抢占一个写位置，抢到之后各自写入，写完再用 CAS 推进提交指针。消费者只读提交指针以内的数据，不会读到写入了一半的内容。

```c
typedef struct {
    volatile uint32_t prod_head;   // 生产者抢占的写指针
    volatile uint32_t prod_tail;   // 生产者提交的写指针
    volatile uint32_t cons;        // 读指针，只有消费者写
    uint32_t           capacity;   // 容量，必须是 2 的幂
    uint8_t            buffer[];   // 柔性数组，调用方分配
} mimi_ringbuffer;
```

三个指针分工明确：

- `prod_head`：生产者抢到的最远写位置，谁 CAS 成功谁先写。
- `prod_tail`：已经写完、可以读的位置，写完了才提交到这里。
- `cons`：消费者读到的位置，只有消费者修改它，不需要原子操作。

![[无锁队列.svg|85%]]

写入流程：

```c
mimi_err mimi_ringbuffer_write(mimi_ringbuffer *ring, const void *buf, uint32_t len)
{
    uint32_t old_head, new_head;
    if (update_prod_head(ring, len, &old_head, &new_head) != MIMI_EOK) {
        return MIMI_ERROR;                  // 空间不够
    }
    // 申请到位置，往自己那一段写数据，处理环绕
    ...
    update_prod_tail(ring, old_head, new_head);   // 提交
    return MIMI_EOK;
}
```

申请写位置用 CAS 自旋：

```c
static mimi_err update_prod_head(mimi_ringbuffer *ring, uint32_t len,
                                 uint32_t *old_head, uint32_t *new_head)
{
    do {
        *old_head = ring->prod_head;
        if (get_space(ring) < len) {
            return MIMI_ERROR;              // 没空间
        }
        *new_head = *old_head + len;
    } while (!CAS(&ring->prod_head, *old_head, *new_head));   // 抢位置
    return MIMI_EOK;
}
```

这就是无锁的含义：`prod_head` 靠 CAS 原子推进，多个生产者同时写也不会互相覆盖，每个生产者都拿到一段独占的空间。消费者读 `prod_tail` 之前的数据，这些数据已经提交完毕，是完整的。

两个细节：

1. `capacity` 必须是 2 的幂。这样取模可以用位与 `& (capacity - 1)`，省一条除法。
2. 提交指针 `prod_tail` 可能乱序推进。两个生产者先后申请位置，先申请的可能后写完，所以提交时用 CAS 自旋，等自己那段前面的都提交了才推进。消费者只看 `prod_tail`，不会读到后写先提交的乱序数据。

### 中断也可以用

无锁队列最大的价值，是中断里也能安全地写。

信号量和消息队列在中断里其实也能用，但它们内部要关中断、操作链表、唤醒线程，路径更长。无锁队列只有 CAS 和 memcpy，没有锁、没有阻塞、没有线程挂起，天然适合中断上下文。

上一章提到过：SysTick 超时回调在中断上下文里执行，回调里不能做耗时操作。有了无锁队列，中断里输出日志就是往 ringbuffer 写一段字节，再调用 `mimi_sem_release` 通知日志线程去取。写入是原子的，唤醒由线程完成。

# 例子

三个机制讲完了，看两个实际组合的例子。

## 异步 log 模块

第三章的日志是同步的，`printf` 直接输出到串口。串口发送是慢操作，一个线程打印一行，整个线程就阻塞在串口发送上，等发送完成才能继续。

这一章把日志改成异步的：写日志只往无锁队列里写字节，写完就返回；一个专门的日志线程负责把队列里的字节输出到串口。

```c
struct {
    mimi_ringbuffer ring;
    uint8_t buffer[MIMI_LOG_BUFFER_SIZE];
} log_ringbuffer;

mimi_sem log_sem;
```

写日志先格式化到临时缓冲，再写进 ringbuffer，最后 release 信号量：

```c
void mimi_log_printf(char level, const char *fmt, ...)
{
    char print_buffer[LOG_TEMP_BUFFER_SIZE];
    // 拼上时间戳、级别、线程名
    ...
    if (mimi_ringbuffer_write(&log_ringbuffer.ring, print_buffer, len) == MIMI_EOK) {
        mimi_sem_release(&log_sem);   // 通知日志线程有活了
    }
}
```

日志线程阻塞在信号量上，被唤醒就把队列读空，交给输出函数：

```c
void mimi_log_thread_entry(void *param)
{
    while (1) {
        mimi_sem_take(&log_sem, MIMI_TIMEOUT_FOREVER);
        while ((len = mimi_ringbuffer_read(&log_ringbuffer.ring,
                read_buffer, LOG_TEMP_BUFFER_SIZE)) > 0) {
            mimi_log_output_func(read_buffer, len);
        }
    }
}
```

这里信号量和无锁队列各司其职：信号量表示有日志到达，唤醒日志线程；无锁队列保存日志字节。写日志的调用方可能是任何线程甚至中断，只做两件事：写 ringbuffer、release。真正访问串口的只有日志线程，串口的慢被隔离在这个线程里，不影响其他线程。

中断里也能输出日志了。日志线程被唤醒前，中断写入队列的字节已经完整，等日志线程醒来统一输出，这正是第三章说的把工作交给线程处理。

## 简易控制台

有了异步日志，再加一个命令解析线程，就是个简易控制台。串口收到一行命令，交给控制台线程，匹配注册的命令，执行对应函数。

命令注册沿用了自动初始化的思路，把命令函数地址放到 `.mimi_cmd_fn` 段：

```c
#define MIMI_CMD_EXPORT(cmd, fn)                                \
    const char __mimi_cmd_##cmd[] = #cmd;                       \
    mimi_used const struct mimi_cmd_desc __mimi_cmd_desc_##fn   \
        mimi_section(".mimi_cmd_fn") = { __mimi_cmd_##cmd, fn };
```

业务代码里加一条命令：

```c
int sem_test(void) { ... }
MIMI_CMD_EXPORT(semtest, sem_test);
```

控制台线程轮询输入，收到一行就去命令段里查名字，匹配就执行：

```c
void mimi_console_thread_entry(void *param)
{
    while (1) {
        uint16_t len = mimi_console_input_func(console_buffer, CONSOLE_TEMP_BUFFER_SIZE);
        mimi_console_input((const char *)console_buffer, len);
    }
```

## 基础用例演示

这一章用单元测试验证信号量、互斥锁、消息队列的状态转换，用真实线程验证无锁队列的并发写。

| 模块 | 验证内容 | 验证方式 |
| ---- | -------- | -------- |
| 信号量 | 计数增减、减到 0 阻塞、超时返回、唤醒队首 | 单元测试 |
| 互斥锁 | 加解锁、递归、非持有者解锁被拒绝、优先级继承接口 | 单元测试 |
| 消息队列 | 收发、环形回绕、空阻塞、满拒绝 | 单元测试 |
| 无锁队列 | 2 的幂容量、环绕、多生产者数据完整性 | 单元测试 + 多线程 |

单元测试用 Unity 框架，跑在 native 环境，不依赖硬件，执行 `pio test -e unit`。

无锁队列的并发写比较特殊：要真正确认多生产者同时写不丢数据，得用多个真实线程并发写。测试里用 Win32 的 `CreateThread`（Linux 上是 pthread）创建 4 个生产者，每个往同一个 ringbuffer 写带线程编号的字节，消费者读出后按编号分类核对，确认每个生产者写入的字节一个没丢、顺序也没乱。

三个例子 `semaphore.c`、`mutex.c`、`msgqueue.c` 则跑在板子上，通过控制台命令触发。互斥锁的例子最直观：两个线程各加 50 次 `shared_cnt`，串口打印的计数应该严格递增到 100，中间不会重复、不会跳变。不加锁的话，很快就能看到计数错乱。

# 主流 RTOS 的同步与通信

主流 RTOS 的同步原语大同小异，差异主要在消息传递的形式：

| RTOS | 信号量 | 互斥锁 | 消息传递 |
| ---- | ------ | ------ | -------- |
| mimiOS | 计数信号量（带上限） | 递归 + 优先级继承 | 固定长度消息队列 + 无锁字节流 |
| **FreeRTOS** | binary / counting / mutex 三种 | 递归，有优先级继承 | `xQueue` 按字节长度可变，复制数据 |
| **RT-Thread** | 计数信号量 | 优先级继承 | `rt_mq` 固定长度 / mailbox 固定 4 字节指针 |
| **Zephyr** | 计数信号量 | 优先级继承（可选配） | `k_msgq` 固定长度 / `k_pipe` 字节流 |
| **ThreadX** | 计数信号量 | 优先级继承 + 可选优先级天花板 | `tx_queue` 固定长度 |

消息队列大多固定长度，FreeRTOS 例外，按字节长度可变。字节流这条路线各家叫法不同，Zephyr 叫 `k_pipe`，DPDK 叫 ring buffer，本质都是 mimiOS 无锁队列这套模型：生产者申请位置并提交，消费者只读已提交的部分。
